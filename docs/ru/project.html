Коротко#

  • Тебе дают готовые серверы ключей (TCPServer, UDPServer — каждый хранит одну пару ключ = значение) и клиентов (TCPClient, UDPClient). Менять их нельзя.
  • Ты пишешь программу Proxy, которая объединяет много серверов и других proxy в одну сеть: клиент спрашивает любой proxy и получает ответ так, будто спросил «весь мир», — независимо от протокола (например, TCP-клиент ↔ UDP-сервер).
  • Нужно спроектировать и описать свой протокол между узлами proxy.
  • Баллы: от 150 (один протокол, без других proxy) до 500 (оба протокола, любая сеть proxy с циклами).
  • Без документации в PDF проект не оценивают. Проекты проверяют антиплагиатом.
⚠️ВниманиеНа этой странице нет готового решения ✍️ от автора

Проекты проходят через антиплагиат, а за плагиат ставят отрицательные баллы — если много людей скопирует один и тот же код с открытого сайта, пострадают все. 🔁Откуда задание (исходное задание с занятий, кратко)

Спецификация 2025/26 рассказывает историю планеты «Нумерландии», где жители и хранители знаний говорят на двух языках (TCP и UDP), а мудрый правитель строит сеть посредников, которые знают оба языка и обмениваются знаниями. Ниже — то же самое простыми словами. Уточни у преподавателя, такая ли спецификация в твоём наборе — она могла измениться.

Что дано (это не меняешь)#

Запуск выданных программ#

  • Каждый сервер хранит один ключ. Во всей сети для каждого имени ключа не больше одного сервера.
  • TCP-клиент говорит только с TCP-сервером, UDP-клиент — только с UDP. Клиент отправляет одну команду, читает один ответ и завершается.
  • Серверы не держат соединений — обрабатывают запросы по очереди.

Базовый протокол клиент–сервер#

Каждая команда и каждый ответ — одна строка текста. В UDP всё сообщение помещается в одну датаграмму.

КомандаОтветЗаметки
GET NAMESOK <число> <имя1> <имя2> …базовый сервер всегда OK 1 <свой ключ>
GET VALUE <имя>OK <значение> или NANA = у меня такого ключа нет
SET <имя> <значение>OK или NAменяет значение ключа
QUITответа нетсервер завершает работу
что угодно другоеNA

Что должен делать твой proxy#

  • -port — порт, на котором proxy слушает сразу по TCP и UDP (для клиентов и других proxy).
  • -server адрес порт — минимум один раз, может быть много раз: узел, к которому proxy должен подключиться, — сервер ключей или другой proxy. Одна и та же пара может быть указана нескольким proxy.
  • Proxy может говорить напрямую только с узлами из параметров; до остальных добирается через другие proxy.
  • Неверные или недостающие параметры → сообщение об ошибке и завершение программы.

После запуска proxy:

  1. Открывает порт TCP и UDP для клиентов и других proxy.
  2. Связывается с узлами из параметров и выясняет, какие из них серверы, а какие proxy, и какой протокол у каждого сервера.
  3. Собирает информацию, какие ключи есть в сети и как до них добраться (какой сервер или через какой proxy).
  4. Обслуживает клиентов обоих протоколов:
    • GET NAMES → список всех ключей сети (внимание на счётчик на второй позиции!),
    • GET VALUE / SET → передаёт в сеть так, чтобы дошло до нужного сервера, и возвращает клиенту его ответ; если такого ключа в сети нет, может сразу ответить NA,
    • QUIT → передаёт дальше в сеть и выключает свои серверы, потом завершается сам.
  5. Proxy не хранит значения ключей — он только знает, где они.

План построения proxy по шагам ✍️ от автора#

Надёжнее всего строить проект этапами — каждый этап это рабочая программа на определённое число баллов.

  1. Параметры. Прочитай -port и список -server адрес порт. Проверь числа и полноту; ошибка → сообщение и System.exit(1).
  2. Слушать TCP и UDP на одном номере порта (это два разных порта — см. C5). Каждый запрос в своём потоке.
  3. Один обработчик команд — одна функция получает строку текста и возвращает строку ответа, независимо от того, пришла она по TCP или UDP.
  4. Определение серверов и таблица ключей: имя → (адрес, порт, протокол, вид узла).
  5. GET NAMES / GET VALUE / SET / QUIT для серверов из параметров → это уже 150–300 баллов.
  6. Общение с другими proxy: придумай свои команды (представиться, обменяться списком ключей, передать запрос). Сеть в виде дерева → 300–400 баллов.
  7. Циклы: идентификатор запроса + память «уже видел» + лимит переходов → 500 баллов.
  8. Документация протокола (ниже) и тестовые скрипты.

Ещё советы ✍️ от автора#

  • Счётчик в GET NAMES: OK 3 a b c — число должно равняться количеству имён, и каждое имя должно встречаться один раз (в сети с циклом легко получить дубликаты — используй Set).
  • Потоки и общие данные: таблицу ключей читают и меняют много потоков → ConcurrentHashMap, ConcurrentHashMap.newKeySet().
  • Взаимная блокировка в цикле: если P1 ждёт ответа P2, а P2 в это же время спрашивает P1 — при обработке в одном потоке обе стороны ждут вечно. Каждый запрос — в своём потоке, и везде таймауты.
  • Порядок запуска: proxy может стартовать раньше сервера — периодически повторяй определение (как в C1).
  • Логи: печатай каждое отправленное и полученное сообщение с именем узла — при 5 открытых окнах это единственный способ что-то понять.
  • Не придумывай слишком хитрый протокол: простой и хорошо описанный протокол лучше хитрого и непонятного — за описание протокола тоже снимают баллы.

Тестовые скрипты#

Скрипты предполагают, что в папке лежат выданные TCPServer, UDPServer, TCPClient, UDPClient и твой Proxy. Порты можно менять.

Список случаев для проверки:

  • GET NAMES с любого proxy даёт все ключи, каждый один раз, с правильным счётчиком,
  • GET VALUE для ключа на TCP-сервере и на UDP-сервере, спрашивая и по TCP, и по UDP,
  • SET, потом GET VALUE с другого proxy показывает новое значение,
  • неизвестный ключ → NA, неверная команда → NA,
  • в сети с циклом ничего не зацикливается (proxy не грузит процессор, логи заканчиваются),
  • QUIT останавливает все proxy и серверы,
  • неверные параметры Proxy → ошибка и завершение.

Документация — как её написать#

Самая важная часть документации — описание протокола. Шаблон преподавателя говорит прямо: описание должно позволить кому-то написать свой proxy на другом языке, и общим будет только разговор по сети. Образец — документ RFC. Классы, методы и переменные Java не описываем.

Проверь себя ✍️ от автора#

❓Проверь себяПочему proxy не может просто запомнить значения ключей?

Потому что спецификация это запрещает — значения живут только на серверах (а SET меняет их в одном месте). Запомненная копия быстро устареет.

❓Проверь себяUDP-клиент спрашивает proxy о ключе, который хранится на TCP-сервере. Что делает proxy?

Получает датаграмму, распознаёт команду, смотрит в таблицу, подключается по TCP к нужному серверу (или пересылает другому proxy), получает строку ответа и отправляет её UDP-датаграммой на адрес и порт клиента.

❓Проверь себяКак не дать запросу бесконечно кружить в сети с циклом?

У каждого запроса уникальный идентификатор; proxy помнит идентификаторы уже обработанных запросов и при повторе отвечает NA (не пересылая дальше). Плюс лимит переходов (TTL).

📝 Конспект: Проект — сеть proxy, соединяющая TCP- и UDP-серверы

Базовые команды#

GET NAMES → OK n k1 … kn · GET VALUE k → OK v/NA · SET k v → OK/NA · QUIT → (ничего) · другое → NA.

Запуск#

java Proxy -port P -server host port [-server host port ...] — неверный параметр → ошибка + exit.

Баллы#

150 (1 протокол, без proxy) · 300 (2 протокола, без proxy) · 300 (1 протокол, дерево) · 400 (2 протокола, дерево) · 500 (2 протокола, циклы). Заявил → должно работать всё, иначе 0.

Архитектура#

  1. параметры → 2. слушатели TCP+UDP (потоки) → 3. один обработчик команд → 4. определение + таблица ключей → 5. пересылка с таймаутами → 6. протокол proxy–proxy → 7. ID + seen + TTL (циклы) → 8. QUIT всем.

Ловушки#

  • UDP к UDPServer: пробел в конце команды.
  • ответы: одна строка; UDP ≤ 256 B.
  • QUIT: не ждать ответа.
  • проверяй команды (неполные убивают сервер).
  • GET NAMES: уникальные имена + верный счётчик.
  • таймауты везде; ConcurrentHashMap.

Сдача#

javac *.java без пакетов · только твои .java + скрипты + «Dokumentacja (номер индекса).pdf» · localhost · без хардкода IP/портов · GAKKO до срока.
