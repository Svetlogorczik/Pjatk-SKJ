Коротко#

  • TCP: соединение, надёжность, порядок — но это поток байт (границы сообщений делаешь сам, например концом строки).
  • UDP: без соединения, без гарантий — зато один send() = одна датаграмма = один receive().
  • В UDP отвечаешь отправителю на адрес и порт, записанные в полученном пакете (getAddress(), getPort()).
  • Из полученного пакета бери только getLength() байт — остальное в буфере мусор.
  • UDP не скажет, что пакет потерялся — сам ставь setSoTimeout.

🎈АналогияTCP — это телефонный звонок, UDP — это SMS ✍️ от автора

При звонке ты сначала соединяешься, потом разговор идёт, и ты слышишь всё по порядку. SMS отправляешь без соединения — каждое отдельная «посылка», может прийти не по порядку или не прийти вовсе.

UDP в Java#

  1. Сокет: сервер new DatagramSocket(port) (фиксированный порт), клиент new DatagramSocket() (любой свободный порт).
  2. Отправка: превращаем текст в байты (getBytes(UTF_8)), упаковываем в new DatagramPacket(байты, длина, адрес, порт), вызываем send.
  3. Приём: готовим пустой пакет с буфером (new DatagramPacket(new byte[1500], 1500)), вызываем receive — метод ждёт.
  4. Чтение: new String(p.getData(), 0, p.getLength(), UTF_8) — только getLength() байт!
  5. Ответ: на p.getAddress() и p.getPort() из полученного пакета.
🐞Частая ошибкаЛовушки UDP ✍️ от автора
  • new String(p.getData()) без длины — получишь текст плюс мусор / нули из остатка буфера.
  • Тот же объект DatagramPacket, повторно использованный для receive, имеет уменьшенную длину — по размеру прошлого сообщения, и более длинное сообщение обрежется. Создавай новый пакет в цикле или вызывай p.setLength(buffer.length).
  • Сообщение длиннее буфера обрезается без всякой ошибки.
  • Без setSoTimeout клиент ждёт потерянный ответ вечно.
  • У TCP и UDP отдельные номера портов: на TCP 6000 и UDP 6000 одновременно могут работать разные программы (пригодится в проекте — proxy слушает оба).

✍️Добавлено автором сайта — этого нет в лекцииПочему первое измерение самое долгое?

На первом пакете Java «разогревается» (загрузка классов, JIT-компиляция), а система готовит структуры для нового сокета. Хороший пример того, что одного измерения мало — для RTT считают среднее (см. EstimatedRTT в C7).

Если отправить датаграмму на порт, где никто не слушает, на Linux ты просто увидишь datagram lost (no answer within 1 s) — UDP ошибку не сообщит.

Два канала сразу: Coordinator и Worker#

Две программы говорят одновременно по TCP и UDP:

КаналНаправлениеСообщение
TCPCoordinator → WorkerTASK <раунд> <a> <b>
UDPWorker → CoordinatorRESULT <раунд> <a+b>
TCPCoordinator → WorkerACK <раунд> OK или ACK <раунд> BAD
TCPCoordinator → WorkerBYE (после 5 раундов)

Кто что слушает?

  • Coordinator: TCP 6100 (ServerSocket) и UDP 6101 (DatagramSocket(6101)).
  • Worker: подключается по TCP к 6100, а его UDP-сокет на любом порту — шлёт на 6101.

Задания#

🎯Задание1. Статистика RTT

Измени UdpPing, чтобы он отправлял 10 пакетов и в конце печатал минимум, максимум и среднее RTT.

✅Показать решение

Держи double min = Double.MAX_VALUE, max = 0, sum = 0; int ok = 0; и после каждого ответа обновляй: min = Math.min(min, rtt); max = Math.max(max, rtt); sum += rtt; ok++;. В конце sum / ok (осторожно с ok == 0, когда всё потерялось).

🎯Задание2. Потерянные датаграммы и повторы

В UdpMirror случайно не отвечай на 30% сообщений (if (Math.random() < 0.3) continue;). Добавь в UdpPing повтор (максимум 3 попытки) после таймаута.

✅Показать решение

Оберни отправку и приём циклом for (int attempt = 1; attempt <= 3; attempt++) { send; try { receive; break; } catch (SocketTimeoutException e) { log("retry " + attempt); } }. Ровно это TCP делает за тебя автоматически.

🎯Задание3. Слишком маленький буфер

Отправь в UdpMirror текст длиннее 1500 байт (например, 2000 символов x). Что получит сервер?

✅Показать решение

Сервер получит только первые 1500 байт — остаток датаграммы пропадёт без исключения. Вывод: задай в протоколе максимальный размер сообщения (в проекте выданные программы используют буфер 256 байт!).

🎯Задание4. Ответ по UDP

Пусть Coordinator отправляет ACK не по TCP, а по UDP на адрес и порт, с которых пришёл RESULT. Что должен изменить Worker?

✅Показать решение

Coordinator: udp.send(new DatagramPacket(ack, ack.length, p.getAddress(), p.getPort())). Worker после отправки RESULT должен вызвать udp.receive(...) на том же UDP-сокете (его порт записан в пакете) и поставить таймаут. TCP-канал тогда нужен только для заданий и BYE.

📝 Конспект: TCP и UDP вместе — поток против датаграмм

UDP — рецепт#

  • Сервер: DatagramSocket s = new DatagramSocket(port);
  • Клиент: DatagramSocket s = new DatagramSocket(); s.setSoTimeout(1000);
  • Отправить: byte[] b = text.getBytes(UTF_8); s.send(new DatagramPacket(b, b.length, InetAddress.getByName(host), port));
  • Принять: DatagramPacket p = new DatagramPacket(new byte[1500], 1500); s.receive(p);
  • Текст: new String(p.getData(), 0, p.getLength(), UTF_8)
  • Ответить: new DatagramPacket(b, b.length, p.getAddress(), p.getPort())

TCP vs UDP#

TCPUDP
соединениеданет

Ловушки#

  • всегда getLength();
  • новый пакет для каждого receive (или setLength);
  • маленький буфер = обрезанное сообщение без ошибки;
  • TCP-порт и UDP-порт с одним номером — это два разных порта.
